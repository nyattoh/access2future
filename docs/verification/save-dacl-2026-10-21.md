# Windows atomic export: DACL and permission fallbacks

Current change base: `d27e7b86d9b193853d75d63b83ca6d3e62f63a61`, PR #13 branch `fix/save-atomic-replace-20261020`. Implementation provider: Codex (`gpt-6.1-sol`).

## Approved contract (2026-10-21 07:24 JST)

This approval supersedes the previous prohibition on ACL-ignore flags and replacing moves, specifically for permission failures on an existing destination. The file is still staged beside the destination, written completely, flushed, size-checked and closed before commit. The bounded `.{uuid}.tmp` name is retained. The Windows contract below is unchanged by the later Unix-mode fix. Unix still commits with `fs::rename`, now with the mode and ownership checks described below.

1. Existing regular file: first call `ReplaceFileW` with flags **0**, preserving the old DACL on the normal path.
2. Only when this first call fails with `ERROR_ACCESS_DENIED` (5), `ERROR_NETWORK_ACCESS_DENIED` (65), or `ERROR_PRIVILEGE_NOT_HELD` (1314), retry the same replacement with `REPLACEFILE_IGNORE_MERGE_ERRORS | REPLACEFILE_IGNORE_ACL_ERRORS` (**0x6**).
3. If that retry fails, call `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH` (**0x9**). No copy flag or in-place destination write is used.

**DACL preservation is not guaranteed on the approved permission fallback paths.** The Microsoft API explicitly documents this limitation for ACL-ignore flags. New destinations, and a first-call error 2 after a destination disappears, still use no-replace moves. Other first-call errors do not enable the permission fallbacks.

If every replacement/move fails, the previous destination bytes remain unchanged under ordinary failure states and staging is cleaned up. A documented error **1177** from either replacement can leave the old file at `.{uuid}.bak`. If the final fallback also fails, that old file is restored with a no-replace move. If the OS refuses restoration, the original bytes/DACL remain in that backup, it is not deleted, and the returned error identifies its recovery path and each failed operation. This is an explicit recovery-error state, not a claim that the original pathname can always be restored despite OS denial. Successful commits do not become failures solely because backup cleanup fails. Hardware/crash recovery is not guaranteed.

References: [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew), [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

## Unix mode regression fix (base `3483dbb`)

The P1 review found that replacing an existing `0600` export with an ordinary staged inode could change it to `0644`. For an existing **regular file**, the Unix path now applies its mode to the empty stage before writing private bytes, then re-reads the destination metadata and reapplies its current mode immediately before rename. New destinations keep the staged creation mode and existing umask behaviour.

The old file's uid/gid are **not** copied and no `chown` or privilege escalation is attempted. If an existing regular file's uid **or** gid differs from the staged file, overwrite is refused with `PermissionDenied`; the old destination stays unchanged and the shared transaction removes the stage. This avoids silently transferring ownership or group. The ownership decision logic is unit-tested; alternate-user filesystem ownership was not changed by the tests. POSIX ACLs and extended attributes are not copied or claimed preserved.

`symlink_metadata` distinguishes a symlink from its target. As before, rename replaces a symlink entry without changing its target; target mode/ownership is not adopted. Destination metadata is checked just before commit, but the metadata-check/rename sequence is not a cross-process compare-and-swap; concurrent external changes remain a boundary.

Windows replacement functions, Windows tests and dependency files have no changes from `3483dbb`; the new preparation hook and module are Unix-cfg only.
